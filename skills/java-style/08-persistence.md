# 08 事务、持久化与缓存

## 1. 事务边界

1. `@Transactional` 只标在 Service 的 `public` 方法上；同类内部自调用不经过代理，事务不生效。
2. 查询方法加 `readOnly = true`；只读事务能减少脏读风险并给数据库优化空间。
3. 事务内禁止：远程调用（HTTP/RPC）、发 MQ、大文件读写、超过 1000 条的批量写、长耗时计算。
4. 捕获异常后要继续抛或显式标记回滚；吞掉异常会导致事务提交：
   ```java
   catch (BizException e) {
       TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
       throw e;
   }
   ```
5. 传播行为显式声明：`REQUIRES_NEW` 只用于独立日志、补偿、审计等必须独立提交的场景，并注释原因。
6. 事务与缓存/消息的顺序：先提交事务，再删除缓存、再发消息；不接受「先发消息后提交」。

## 2. MyBatis

1. 参数一律 `#{}`；`${}` 只允许用于白名单校验过的排序字段或表名，并在注释里写明校验位置。
2. 禁止 `SELECT *`；列显式列出，避免表结构变更导致的隐式行为。
3. 分页必须带；深分页（大 offset）改用游标（`where id > ?`）或延迟关联。
4. 批量写入分批：单批 500–1000 条，或使用 `ExecutorType.BATCH`；不要在一条 SQL 里塞上万参数。
5. 警惕 N+1：关联数据用 join 或按 id 批量 `IN` 查询；禁止在循环里调用 Mapper。
6. `IN` 参数有上限（Oracle 1000），超过要分批。
7. 结果映射显式 `resultMap`；不依赖自动映射猜测字段（尤其下划线转驼峰配置不一致时）。
8. 枚举持久化用 `@EnumValue` 或自定义 `TypeHandler`，不用 `ordinal()`。
9. 动态 SQL 的 `<if>` 条件要防止全表更新/删除：`<where>` 与参数校验双保险。

## 3. 缓存

1. Key 规范：`业务:实体:版本:id`，例如 `order:detail:v1:123`；版本号用于结构变更时整体失效。
2. 必须设置过期时间；永不过期的缓存视为缺陷（除非有明确的主动失效机制）。
3. 三防：
   - 穿透：不存在的数据缓存空值 + 短 TTL（30–60 秒）。
   - 击穿：热点 key 重建加互斥锁，或逻辑过期 + 异步重建。
   - 雪崩：TTL 加随机抖动（±10%），避免同一秒集体失效。
4. 更新策略：Cache-Aside，先更新数据库再删除缓存；需要在删除失败时重试或走补偿。
5. 缓存对象不可变、可序列化，避免缓存大对象与全量列表；分页数据按页缓存并限制页数。
6. 本地缓存（Caffeine）与分布式缓存（Redis）职责分清：本地缓存只放允许短暂不一致的数据，并设置小容量与短过期。

## 4. 数据一致性

1. 跨服务一致性用本地消息表或事务消息；不接受「先发消息再提交事务」。
2. 对账与补偿任务必须幂等（业务唯一键 + 状态机），可重复执行。
3. 状态流转用状态机（枚举 + 显式转移表）校验，禁止任意 `setStatus`。
4. 删除用逻辑删除时，唯一索引要包含删除标记或用「删除时间戳」避免重复键冲突。
5. 金额、库存等强一致字段用数据库条件更新（`where stock >= ?`）而不是先查后改。

## 5. 连接与资源

1. 连接池参数可配（最大连接、最小空闲、获取超时）；获取连接必须有不小于业务超时的上限。
2. 不在事务内嵌套获取多个连接；批量任务单独控制并发度。
3. 慢 SQL 必须有监控与阈值告警；上线前用 `EXPLAIN` 确认索引命中。
