# 最小化职能与命名契约

## 1. 拆分轴：变更原因，不是实体

同一个领域对象被谁操作、因为什么被改，才是边界。

| 拆分轴 | 结果 | 症状 |
|---|---|---|
| 按实体（一张表一个 Service） | 一个 1200 行的服务，改报表碰计费，改计费碰审计 | 每次改动都要回归全部功能 |
| 按变更原因（谁会要求它改） | 查询、出账、审计、统计、退款各自独立 | 加功能只动一个服务 |

一句话判据：**这些代码会因为同一个原因改变吗？** 会 → 同一个服务；不会 → 拆开。

接口方法数不是唯一的拆分依据，但**接口宽度 ≈ 实现宽度**就是浅模块信号：一个 70 方法的接口后面接 1200 行实现，说明它是页面视图的目录，不是模块。

## 2. 案例：同一张表的 5 个服务

| 接口 | 方法数 | 只负责 | 谁会让它改 |
|---|---|---|---|
| 查询服务 | 36 | 列表 / 明细 / 收款登记 | 前端加了新页面、新统计口径 |
| 出账服务 | 21 | 生成、终止收口、退租预览 | 计费规则变了 |
| 审计服务 | 4 | 全部变更流水 | 审计字段或流水类型变了 |
| 统计服务 | 5 | 汇总指标 | 报表口径变了 |
| 退款服务 | 5 | 退款流程 | 退款规则变了 |

审计服务只有 4 个方法却独立存在，理由是：**调用方最多**（出账、收款、终止、作废、编辑都要调），而且它的失败代价与业务失败不同——摊进各业务服务就等于同一条规则有 6 份。

## 3. 协作三规则

1. **不碰对方的表。** A 服务直接 `UPDATE` B 的表，等于绕过 B 的唯一写入点、税额快照和审计流水。要改就让 B 提供接口。
2. **事务边界留在编排层。** 业务动作的事务由发起方决定，被调服务不自己开新事务。
3. **需要不同边界就显式命名。** 同一逻辑的两种事务语义，用两个入口表达：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public int generateForContractInNewTx(Long id, LocalDate asOf) { return generateForContract(id, asOf); }

@Transactional(rollbackFor = Exception.class)
public int generateForContract(Long id, LocalDate asOf) { ... }
```

`InNewTx` 后缀本身就是注释，而且删不掉。替代方案是 `if (batch) {...}` 这类运行时开关——读代码的人永远不知道当前走哪条。

## 4. 方法细化：下限是「一件事」，不是「一行」

| 抽不抽 | 判据 |
|---|---|
| 抽 | 一段逻辑能在命名后让调用处变成一句话 |
| 不抽 | 一行代码，抽出来只能叫两个字母 |

```java
// 反例：抽出来只能叫 nz，因为它实在没有内容可命名
private static BigDecimal nz(BigDecimal v) { return v == null ? BigDecimal.ZERO : v; }

// 改法：内联，或收进通用工具并起全名
MoneyUtils.zeroIfNull(v)
```

**极端琐碎的方法取不到有信息量的名字，这本身就是「它不该被抽成方法」的信号。** 一行代码抽成方法，只是把可读性问题变成了跳转问题。

## 5. 命名契约前缀表

泛动词（`handle / process / do / deal`）不承诺任何东西，所以必须配注释。前缀动词承诺了调用方**该做什么**：

| 前缀 | 契约 | 调用方可以假设 |
|---|---|---|
| `require*` | 校验通过返回非 null；不通过抛异常 | 不用判空，但要处理异常 |
| `assert*` | 纯前置断言，无返回值，不满足就抛 | 只为副作用调用 |
| `check*` | 校验；不存在与越权同一句文案 | 不会泄露目标是否存在 |
| `validate*` | 结构与取值校验，失败带字段名 | 不改状态 |
| `resolve*` | 查询并兜底，**可能返回 null**，不抛 | 必须判空 |
| `normalize*` | 归一到规范形态，**会改入参** | 不能当纯函数用 |
| `apply*` | 施加一个效果（写值 / 分摊 / 派生） | 有副作用 |
| `record*` | 写审计，返回条数，不阻断主流程 | 可以失败而不影响主流程 |
| `is* / has*` | 纯判定，boolean，无副作用 | 可以放进条件表达式 |
| `count*` | 计数，不抛 | 空集返回 0 |
| `build*` | 组装 VO / 预览，**不落库** | 只读 |
| `write*` | 唯一写入口，返回主键 | 有副作用，且只有这一个入口 |
| `list* / detail* / stats*` | 三档读：列表 / 明细 / 汇总 | 不混用 |

**缺条件就配注释。** 名字里没有「对象」的（`require` 而非 `requireTaxRate`）、没有「范围」的（`build` 而非 `buildTerminatePreview`），注释就得回来。

## 6. 注释只留三种

方法名负责「做什么」，注释只负责名字**无法表达**的信息：

| 类型 | 内容 | 例子 |
|---|---|---|
| **决策理由** | 为什么不用另一种写法 | 「重叠而不是等值：免租顺延 / 收口会让起止变化」 |
| **历史事故** | 踩过什么坑、拒绝过什么诱惑 | 「不为 0 直接拒跑，不做按合同 + 类型 + 期起猜条款的兜底」 |
| **契约边界** | 调用方必须知道的不变量 | 「分母为 0 时返回 null，而不是 0%」 |

**该删的第四种**：复述名字的注释。判据——把注释翻译成中文，如果和方法名意思一样，删。

## 7. Controller 只写契约，不写流程

Controller 方法体应当只有三行：`startPage()` → 调 Service → `getDataTable()`。它的注释不该讲「这是列表接口」，而该讲：

- 新增了哪两个参数、默认值是什么
- 某个参数不传 / 传特殊值分别什么行为
- 与相邻接口（导出、统计卡）是否同一套参数
- 本接口是否受数据范围约束、约束在 Service 还是 Controller

一句话：**流程读代码，边界写注释。**

## 8. 诚实的反例

命名契约不是所有地方都执行到位。真实的反例：

| 现象 | 违反了什么 | 改法 |
|---|---|---|
| `nn(p)` / `nz(v)` | 名字不承诺契约 | `emptyIfNull` / `zeroIfNull`，或内联 |
| `without(p)` / `all(p)` | 只说了半个意思 | `isWithoutTrack` / `isAllTrack` |
| 一个服务 72 个 public 方法 | 浅模块：接口宽度 ≈ 实现宽度 | 按查询维度再分组 |
| 唯一写入口是 `public` 但只被自己调 | 靠约定而非可见性保证 | 改 `private`，或抽成只暴露接口的 Writer 组件 |

**发现反例时的处理**：不要为了「统一」去改存量（那是行为不变的重构，收益低风险高）；在新代码里按契约写，改到哪个文件顺手修哪个文件。
